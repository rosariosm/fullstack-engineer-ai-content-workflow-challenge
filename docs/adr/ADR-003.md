# ADR-003 – Adopt harness engineering for AI-assisted SDLC

## Title & Status

**Title:** ADR-003 – Adopt harness engineering for AI-assisted SDLC  
**Status:** Accepted

## Context

This training engagement includes building a full-stack AI content workflow using **AI-assisted development** — agents write code, tests, and documentation across multiple sessions. Without structure, AI agents exhibit predictable failure modes:

- **Context loss** across sessions — agents forget prior decisions, file locations, and in-progress work
- **Untestable claims** — agents report features as "done" without verifiable evidence
- **State hallucination** — agents assume files, tests, or deployments exist when they do not

The [TRD](../trd.md) plans a **Phase 1 harness scaffold** (`AGENTS.md`, optional `feature_list.json`) and references harness-aligned phased delivery. A primary training goal is practicing an **AI-assisted SDLC** with higher confidence than ad-hoc prompting.

The stack context ([ADR-001](./ADR-001.md) Django, [ADR-002](./ADR-002.md) Strawberry) is fixed; the harness governs *how* agents implement it.

## Options Considered

### Option A: Harness-driven development

Structured agent instructions and progress artifacts in the repository, following harness engineering principles.

**Components (Phase 1+ deliverables):**

| Artifact | Purpose |
|----------|---------|
| `AGENTS.md` | Entry point — stack, conventions, termination criteria, session protocol |
| `feature_list.json` (optional) | Machine-readable feature backlog with pass/fail status |
| `PROGRESS.md` (optional) | Human-readable session notes and handoff context |
| `DECISIONS.md` (optional) | Running log of implementation decisions not captured in ADRs |

**Practices:**

- **WIP=1** — one feature active at a time to reduce context switching and incomplete work
- **3-layer termination check** — syntax/lint → unit tests → E2E before marking a feature complete
- **Clean-state exit protocol** — every session ends with passing tests, committed or staged work, and updated progress notes
- **Sprint contracts** — planner defines scope, generator implements, evaluator verifies

**Pros:**

- Predictable agent behavior across sessions
- Verifiable progress — features marked done only with test evidence
- Clean handoffs between human and agent work
- Aligns with training goal of AI-assisted SDLC best practices

**Cons:**

- Slower initial ramp-up — harness files must be written before implementation accelerates
- Ongoing maintenance of `AGENTS.md`, feature list, and progress notes
- Discipline overhead for a solo developer (Ro) — WIP=1 and exit protocol require self-enforcement

### Option B: Ad-hoc prompting

No structured harness; rely on conversational context, ClickUp tickets, and TRD/PRD docs for agent guidance.

**Pros:**

- Zero upfront harness investment — start coding immediately
- Flexible — no rigid session protocol

**Cons:**

- High risk of context loss and duplicated work across sessions
- No machine-verifiable definition of "done" for agent-generated features
- Agents may hallucinate state or skip tests without explicit termination criteria
- Does not meet the training objective of practicing harness-driven AI development

## Decision

**Adopt harness engineering** for this project, following:

1. The principles in the [Walking Labs harness engineering guide](https://walkinglabs.github.io/learn-harness-engineering/en/) — repo-level artifacts, WIP limits, termination checks, and clean session handoffs.
2. The **NaNLABS agentic harness** — three-layer model combining repo entry points (`AGENTS.md`), local persistent context (`~/.nan-ai-workspace/` packs and knowledge, not committed to the app repo), and NaNLABS skills for delivery orchestration (`nanlabs-dev-companion`, `nanlabs-workflow-generic-project`, and phase-specific skills such as `nanlabs-assistant`).

Walking Labs defines *what* a harness is and how sessions should behave; NaNLABS provides the operational tooling and skill routing that implements it for this training engagement.

Implementation begins in **Phase 1** with `AGENTS.md` as the mandatory repo entry point. NaNLABS skills and the local workspace supply cross-session memory and workflow gates; optional repo artifacts (`feature_list.json`, `PROGRESS.md`, `DECISIONS.md`) are added as needed. ClickUp remains the source of truth for ticket status and delivery progress; the harness governs agent session behavior within the repo.

This ADR documents the decision only. Harness files are created in Phase 1 — not in this ADR deliverable.

## Consequences

**Positive:**

- **Predictable agent behavior** — agents read `AGENTS.md` first and follow defined termination criteria
- **Higher confidence in "done"** — 3-layer checks (syntax → unit → E2E) before features are marked complete
- **Clean session handoffs** — exit protocol ensures the next session starts from a known-good state
- **Audit trail** — progress notes and decision logs supplement ClickUp for implementation detail

**Negative / trade-offs:**

- **Slower ramp-up** — Phase 1 must scaffold harness before feature velocity peaks
- **Maintenance burden** — harness files need updates as stack and conventions evolve
- **Solo enforcement** — WIP=1 and exit protocol rely on developer discipline without a team to catch violations

**Operational practices adopted:**

| Practice | Rule |
|----------|------|
| WIP limit | One active feature at a time |
| Termination | Syntax/lint pass → unit tests pass → E2E pass (where applicable) |
| Session exit | Clean git state, updated progress, no failing tests |
| Sprint roles | Planner (scope) → Generator (implement) → Evaluator (verify) |

# ADR-002 – Use Strawberry GraphQL

## Title & Status

**Title:** ADR-002 – Use Strawberry GraphQL  
**Status:** Accepted

## Context

The ACME challenge requires a **GraphQL-only application API** — all product queries, mutations, and real-time updates flow through a single `/graphql/` endpoint. The client has selected **Strawberry** as the GraphQL library for the Django backend ([ADR-001](./ADR-001.md)).

Additional context:

- The client chose Strawberry for its **Pythonic approach**: type hints, dataclasses, and schema-as-code that reads like native Python rather than a separate DSL.
- The [TRD](../trd.md) defines the GraphQL schema (Campaign, ContentPiece, AISuggestion types), review mutations (`transitionReviewStatus`), AI mutations (`generateDraft`, `translateContent`), nested queries, and **subscriptions** for dashboard real-time updates.
- **graphene-django** is the incumbent alternative in the Django ecosystem but was not selected for this engagement.
- The frontend uses Apollo Client against `/graphql/`; the backend must expose a typed, introspectable schema.

## Options Considered

### Option A: Strawberry GraphQL

Modern Python GraphQL library built on dataclasses and type hints, with first-class Django integration.

**Pros:**

- Native Python schema definition with static type checking support
- Active development and modern async/subscription support
- `strawberry-django` integration for ORM types, filters, and pagination
- Aligns with client mandate and TRD architecture (dedicated `graphql/` app)
- Subscriptions fit the PRD requirement for real-time dashboard updates

**Cons:**

- Smaller community and fewer Stack Overflow answers compared to graphene-django
- Learning curve for developers familiar with REST or graphene's relay patterns
- Subscription setup over WebSockets adds ASGI and infrastructure complexity (TRD notes SSE fallback as contingency)

### Option B: graphene-django

Established GraphQL library for Django with relay conventions and large existing codebase footprint.

**Pros:**

- Long track record in Django projects
- Extensive documentation and community examples
- Relay connection patterns built in

**Cons:**

- Schema definition uses a separate class-based API less aligned with modern Python type hints
- Development pace and async/subscription story lag behind Strawberry
- Conflicts with the client-mandated Strawberry stack
- Would require renegotiating the agreed GraphQL library with the client

## Decision

**Use Strawberry GraphQL** as the API layer, mounted at `/graphql/` via Django's `config/urls.py`.

The schema lives in a dedicated `graphql/` app with resolvers delegating to domain services (`CampaignService`, `ContentService`, `ReviewStateMachine`, `LLMService`). Queries, mutations, and subscriptions are all exposed through Strawberry. This ratifies the client mandate without reopening library selection.

## Consequences

**Positive:**

- **Type-safety:** Schema types map to Python dataclasses; mypy and IDE tooling catch errors at development time
- **Async support:** Strawberry's async resolvers and subscriptions align with real-time dashboard requirements (TRD Phase 5)
- **Clean separation:** GraphQL layer (`graphql/`) stays thin; business logic remains in domain apps (`campaigns/`, `content/`, `ai/`)
- **Apollo Client compatibility:** Standard GraphQL over HTTP/WebSocket works with the chosen frontend stack

**Negative / trade-offs:**

- **Learning curve:** Team members new to GraphQL must learn schema design, resolver patterns, and N+1 query considerations alongside Django ORM
- **Subscription complexity:** WebSocket subscriptions require ASGI deployment and careful connection management; TRD documents an SSE fallback if the spike proves too costly
- **Ecosystem size:** Fewer third-party plugins than graphene for niche GraphQL-Django patterns

**Neutral:**

- GraphQL introspection and GraphiQL (or similar) aid development and agent-assisted coding
- Testing uses pytest with Strawberry test utilities (per TRD testing strategy)

# ADR-001 – Use Django as backend framework

## Title & Status

**Title:** ADR-001 – Use Django as backend framework  
**Status:** Accepted

## Context

The ACME GLOBAL MEDIA AI content workflow challenge specifies a fixed backend stack: **Django + Strawberry GraphQL + PostgreSQL**. This is a client mandate — not an open architectural choice for this engagement.

Additional context:

- A primary training objective is **Learn Django** — upskilling for upcoming client work where Django is the expected framework.
- The [TRD](../trd.md) defines a Django project layout with `config/` (settings, URL routing, ASGI/WSGI) and domain apps (`campaigns/`, `content/`, `ai/`, `graphql/`).
- Product requirements ([PRD](../prd.md)) need persistent entities (Campaign, ContentPiece, AISuggestion), a review state machine, and operational routes (`/health/`, `/admin/`) alongside the GraphQL API at `/graphql/`.
- FastAPI is a common alternative in the Python ecosystem for API-only services but was not selected for this challenge.

## Options Considered

### Option A: Django

Python web framework with batteries-included ORM, migrations, admin, and mature ecosystem.

**Pros:**

- Built-in ORM and migration system map cleanly to PRD entities and PostgreSQL
- Django admin supports data inspection during development (TRD lists `/admin/` as optional P0)
- Strong ecosystem integration with Strawberry (`strawberry-django`), pytest, and ASGI deployment
- Aligns with client mandate and training learning goals
- Standard project structure (`config/`, apps) is well documented and auditable

**Cons:**

- Heavier dependency footprint and startup cost compared to microframeworks
- Real-time GraphQL subscriptions require ASGI deployment (Daphne/Uvicorn) rather than sync WSGI alone
- Django conventions (apps, migrations, settings) apply even when the product API is GraphQL-only

### Option B: FastAPI

Async-first Python microframework popular for REST and API-only services.

**Pros:**

- Lightweight, async-native design
- Fast to scaffold for simple API endpoints
- Growing adoption for greenfield API projects

**Cons:**

- No built-in ORM or admin — would require separate tooling (SQLAlchemy, custom admin)
- Conflicts with the client-mandated Django stack
- Does not serve the training objective of learning Django
- Would require renegotiating the agreed stack with the client

## Decision

**Use Django 5.x** as the backend framework for all server-side logic, persistence, and HTTP routing.

Django provides the ORM, migration pipeline, admin interface, and project structure that the TRD assumes. Strawberry GraphQL mounts on Django via `config/urls.py` at `/graphql/`, with ops routes (`/health/`, `/admin/`) using standard Django views. This ratifies the client mandate without reopening framework selection.

## Consequences

**Positive:**

- Django ORM models align directly with Campaign, ContentPiece, AISuggestion, and ReviewStatus entities defined in the PRD and TRD
- Built-in admin accelerates development and debugging before the React dashboard is complete
- Strawberry integrates with Django through a dedicated `graphql/` app; domain logic stays in service layers (`CampaignService`, `ContentService`, `ReviewStateMachine`)
- Familiar structure for Django developers joining the project

**Negative / trade-offs:**

- Larger dependency surface than FastAPI; Docker images and cold starts are slightly heavier
- GraphQL subscriptions require ASGI configuration — already planned in the TRD
- Team must maintain Django conventions (apps, migrations, settings modules) alongside GraphQL schema evolution

**Neutral:**

- The product API is GraphQL-only; Django REST Framework is not required
- HTTP routing still uses Django's standard `config/urls.py` entry point for both GraphQL and non-GraphQL paths
